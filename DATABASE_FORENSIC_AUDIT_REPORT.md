**Date:** July 23, 2026

**Purpose:** Read-only audit for long-term archival of historical football data (2023–2026 and future seasons)

# Executive Summary

This report provides a comprehensive forensic analysis of the BASHIRI PostgreSQL database to determine the optimal long-term archival strategy for historical football data. The analysis reveals a well-structured Django application with 48 tables across 12 Django apps, containing approximately 4,500+ rows of data with a current storage footprint of ~9.9 MB.

**Key Findings:**
- **Critical Historical Data:** 10 core tables containing irreplaceable football data (leagues, teams, matches, AI performance tracking)
- **Business Data:** 9 tables for user management, subscriptions, payments, and notifications
- **Temporary/Cache Data:** 29 tables that should NOT be archived long-term (sessions, Celery results, tokens, etc.)
- **Current Database Size:** 9.9 MB (with 3,515 matches across 5 leagues, 138 teams, 15 users)
- **Projected 5-Year Growth:** ~50-100 MB assuming continued data collection
- **No Custom Database Objects:** No custom views, triggers, functions, materialized views, or enums (all handled by Django ORM)
- **Single Extension:** Only plpgsql (PostgreSQL procedural language - default)
- **No External Dependencies:** No PostGIS, pgcrypto, or other extensions requiring special handling

# 5. Backup Strategy Recommendations

## 5.1 Critical Historical Data (IRREPLACEABLE)

**Strategy:** Full pg_dump + CSV exports + SQL exports

**Rationale:**
- Multiple formats ensure future compatibility
- pg_dump preserves complete schema, sequences, constraints
- CSV provides human-readable, tool-agnostic format
- SQL provides direct restore capability

**Recommended Commands:**

```bash
# Full pg_dump (schema + data)
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri -F c -f /tmp/bashiri_critical_$(date +%Y%m%d).dump

# CSV exports (for analysis and portability)
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM predictions_league) TO STDOUT WITH CSV HEADER" > leagues.csv
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM predictions_team) TO STDOUT WITH CSV HEADER" > teams.csv
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM predictions_match) TO STDOUT WITH CSV HEADER" > matches.csv
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM predictions_aiperformance) TO STDOUT WITH CSV HEADER" > aiperformance.csv
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM predictions_aitrackrecordsnapshot) TO STDOUT WITH CSV HEADER" > aitrackrecords.csv
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM predictions_activederby) TO STDOUT WITH CSV HEADER" > activederby.csv

# SQL exports (for direct restore)
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri -t predictions_league -t predictions_team -t predictions_match -t predictions_aiperformance -t predictions_aitrackrecordsnapshot -t predictions_activederby -f /tmp/bashiri_critical_$(date +%Y%m%d).sql
```

**Backup Frequency:** Weekly during active seasons, monthly during off-season

**Retention:** Keep all backups indefinitely (they are small)

## 5.2 Business Data (IMPORTANT BUT REPLACEABLE)

**Strategy:** Monthly pg_dump + Quarterly CSV exports

**Rationale:**
- Business data is important for compliance and continuity
- Can be reconstructed from payment processor records if needed
- Less critical than historical football data
- Monthly backup balances risk with storage efficiency

**Recommended Commands:**

```bash
# Monthly pg_dump (business tables only)
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri -t accounts_user -t accounts_user_favorite_teams -t accounts_user_favorite_leagues -t payments_subscription -t payments_transaction -t notifications_preference -t dashboard_adminactionlog -t support_ticket -t support_message -F c -f /tmp/bashiri_business_$(date +%Y%m).dump

# Quarterly CSV exports
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM accounts_user) TO STDOUT WITH CSV HEADER" > users_$(date +%Y%Q).csv
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM payments_subscription) TO STDOUT WITH CSV HEADER" > subscriptions_$(date +%Y%Q).csv
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM payments_transaction) TO STDOUT WITH CSV HEADER" > transactions_$(date +%Y%Q).csv
```

**Backup Frequency:** Monthly

**Retention:** Keep monthly backups for 1 year, quarterly backups for 7 years (compliance)

## 5.3 User-Generated Content (OPTIONAL ARCHIVAL)

**Strategy:** Quarterly pg_dump (optional)

**Rationale:**
- Content can be regenerated from historical match data
- Has value for user engagement analytics but not critical
- Optional archival based on business needs

**Recommended Commands:**

```bash
# Quarterly pg_dump (content tables only)
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri -t feed_card -t feed_pollvote -t chat_message -t chat_usage -t notifications_notification -t matchroom_message -t mic_reaction -t mic_reactionvote -t herocarousel_customslide -t support_contentreport -F c -f /tmp/bashiri_content_$(date +%Y%Q).dump
```

**Backup Frequency:** Quarterly

**Retention:** Keep quarterly backups for 2 years

## 5.4 Temporary/Cache Data (NO ARCHIVAL)

**Strategy:** No backup

**Rationale:**
- Data is ephemeral by design
- Can be regenerated by application
- Includes session data, tokens, task results, Celery configuration
- Archiving this data wastes storage and complicates restores

**Tables to Exclude:**
- `accounts_otpcode`
- `notifications_devicetoken`
- `django_session`
- `django_celery_results_*`
- `token_blacklist_*`
- `django_migrations`
- `django_admin_log`
- `django_content_type`
- `auth_*`
- `django_celery_beat_*`

## 5.5 Full Database Backup (DISASTER RECOVERY)

**Strategy:** Daily automated pg_dump (for disaster recovery only)

**Rationale:**
- Complete database backup for quick disaster recovery
- Not intended for long-term archival
- Should be replaced by selective backups for archival

**Recommended Commands:**

```bash
# Daily automated pg_dump (full database)
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri -F c -f /tmp/bashiri_full_$(date +%Y%m%d).dump

# Rotate daily backups (keep 7 days)
find /tmp/bashiri_full_*.dump -mtime +7 -delete
```

**Backup Frequency:** Daily

**Retention:** 7 days rolling

# 8. Risk Assessment

## 8.1 Orphaned Foreign Keys

**Risk Level:** LOW

**Description:** Foreign key references to non-existent parent records.

**Mitigation:**
- pg_dump and SQL exports maintain referential integrity automatically
- CSV imports require careful ordering and constraint management
- Post-restore verification queries to detect orphans
- Use `SET session_replication_role = 'replica'` during CSV imports to temporarily disable FK checks

**Verification Queries:**
```sql
-- Check for orphaned foreign keys
SELECT COUNT(*) FROM predictions_match WHERE league_id NOT IN (SELECT id FROM predictions_league);
SELECT COUNT(*) FROM predictions_match WHERE home_team_id NOT IN (SELECT id FROM predictions_team);
SELECT COUNT(*) FROM predictions_match WHERE away_team_id NOT IN (SELECT id FROM predictions_team);
SELECT COUNT(*) FROM predictions_team WHERE league_id NOT IN (SELECT id FROM predictions_league);
```

## 8.2 Duplicated Data

**Risk Level:** LOW

**Description:** Duplicate records due to multiple restore operations.

**Mitigation:**
- Use `TRUNCATE` before restore to clear existing data
- Use unique constraints to prevent duplicates
- pg_dump format handles this automatically (drops and recreates tables)
- CSV imports require manual cleanup or use `INSERT ... ON CONFLICT`

**Prevention:**
```sql
-- Truncate tables before CSV import (in reverse dependency order)
TRUNCATE TABLE predictions_match CASCADE;
TRUNCATE TABLE predictions_team CASCADE;
TRUNCATE TABLE predictions_league CASCADE;
```

## 8.3 Missing Lookup Tables

**Risk Level:** LOW

**Description:** Attempting to restore child tables before parent tables.

**Mitigation:**
- Follow dependency order (Level 0 → Level 1 → Level 2 → Level 3)
- pg_dump and SQL exports handle ordering automatically
- CSV imports require manual ordering
- Document dependency order in restoration procedures

**Dependency Order:**
1. Leagues (Level 0)
2. Teams (Level 1)
3. Matches (Level 2)
4. All dependent tables (Level 2+)

## 8.4 Sequence Mismatches

**Risk Level:** MEDIUM

**Description:** Primary key sequences out of sync with actual data, causing duplicate key errors on new inserts.

**Mitigation:**
- pg_dump and SQL exports include sequence state
- CSV imports require manual sequence reset after import
- Always reset sequences after CSV import using max ID

**Sequence Reset Commands:**
```sql
SELECT setval('predictions_league_id_seq', (SELECT MAX(id) FROM predictions_league));
SELECT setval('predictions_team_id_seq', (SELECT MAX(id) FROM predictions_team));
SELECT setval('predictions_match_id_seq', (SELECT MAX(id) FROM predictions_match));
SELECT setval('predictions_aiperformance_id_seq', (SELECT MAX(id) FROM predictions_aiperformance));
SELECT setval('predictions_aitrackrecordsnapshot_id_seq', (SELECT MAX(id) FROM predictions_aitrackrecordsnapshot));
SELECT setval('predictions_activederby_id_seq', (SELECT MAX(id) FROM predictions_activederby));
```

## 8.5 Large Object Handling

**Description:** PostgreSQL large objects (LOBs) for binary data.

**Assessment:** No large objects found in database. All binary data (images, videos) stored externally in Cloudinary.

**Mitigation:** N/A

**Risk Level:** LOW

- All types are standard PostgreSQL types with good cross-version compatibility

## 8.8 Character Encoding Issues

**Description:** Character encoding mismatches causing data corruption.

**Mitigation:**

## 8.9 Time Zone and Timestamp Issues

**Risk Level:** MEDIUM

**Description:** Timestamp timezone mismatches causing data inconsistency.

**Assessment:** Database uses `Africa/Dar_es_Salaam` timezone (from Django settings).

**Mitigation:**

- Use UTC for storage if possible (best practice)
- Include timezone information in backup metadata

## 8.10 Backup Corruption

**Risk Level:** LOW

**Description:** Backup files corrupted during storage or transfer.

**Mitigation:**
- Generate SHA256 checksums for all backup files
- Store checksums in separate location
- Verify checksums before restore
- Use multiple backup formats (pg_dump, SQL, CSV) for redundancy
- Store backups in multiple locations (local + cloud)

# 9. Long-Term Archival Strategy

## 9.1 Archival Principles

1. **Multiple Format Preservation:** Maintain pg_dump, SQL, and CSV formats for future compatibility
2. **Redundant Storage:** Store backups in multiple locations (local + cloud)
3. **Regular Integrity Verification:** Periodic checksum verification and test restores
4. **Documentation:** Comprehensive metadata and restoration procedures
5. **Incremental Backups:** Regular backups to minimize data loss window
6. **External Data Archival:** Archive Cloudinary media (team crests, videos)
7. **Schema Evolution Tracking:** Document schema changes over time
8. **Compliance Retention:** Follow regulatory requirements for business data

## 9.2 Recommended Backup Schedule

### Critical Historical Data
- **Frequency:** Weekly during active football seasons (August-May), monthly during off-season (June-July)
- **Formats:** pg_dump, SQL, CSV
- **Retention:** Indefinite
- **Locations:** Local storage + cloud storage (e.g., AWS S3, Google Cloud Storage)

### Business Data
- **Frequency:** Monthly
- **Formats:** pg_dump, CSV
- **Retention:** 7 years (compliance)
- **Locations:** Local storage + cloud storage

### User-Generated Content
- **Frequency:** Quarterly
- **Formats:** pg_dump
- **Retention:** 2 years
- **Locations:** Local storage

### Disaster Recovery
- **Frequency:** Daily
- **Formats:** pg_dump
- **Retention:** 7 days rolling
- **Locations:** Local storage only

### Cloudinary Media
- **Frequency:** Monthly
- **Formats:** Original files
- **Retention:** Indefinite (for team crests), 2 years (for mic videos)
- **Locations:** Cloud storage + local backup

## 9.3 Storage Recommendations

**Primary Storage:** Local server with RAID configuration  
**Secondary Storage:** Cloud storage (AWS S3, Google Cloud Storage, or similar)  
**Tertiary Storage:** Cold storage (AWS Glacier, Google Cold Line) for archives older than 1 year

## 9.4 Automation Recommendations

### Backup Automation Script

```bash
#!/bin/bash
# backup_bashiri.sh - Automated backup script

DATE=$(date +%Y%m%d)
BACKUP_DIR="/backups"
CRITICAL_DIR="$BACKUP_DIR/critical-historical"
BUSINESS_DIR="$BACKUP_DIR/business"
CONTENT_DIR="$BACKUP_DIR/user-content"
FULL_DIR="$BACKUP_DIR/full-db"

# Create directories
mkdir -p "$CRITICAL_DIR/pg_dump" "$CRITICAL_DIR/sql" "$CRITICAL_DIR/csv/$(date +%Y)/$(date +%m)"
mkdir -p "$BUSINESS_DIR/pg_dump" "$BUSINESS_DIR/csv/$(date +%Y)/Q$((($(date +%-m)-1)/3+1))"
mkdir -p "$CONTENT_DIR/pg_dump"
mkdir -p "$FULL_DIR"

# Critical historical data backup
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri -t predictions_league -t predictions_team -t predictions_match -t predictions_aiperformance -t predictions_aitrackrecordsnapshot -t predictions_activederby -F c -f /tmp/bashiri_critical_$DATE.dump
docker cp bashiri_db:/tmp/bashiri_critical_$DATE.dump "$CRITICAL_DIR/pg_dump/"

# CSV exports
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM predictions_league) TO STDOUT WITH CSV HEADER" > "$CRITICAL_DIR/csv/$(date +%Y)/$(date +%m)/leagues.csv"
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM predictions_team) TO STDOUT WITH CSV HEADER" > "$CRITICAL_DIR/csv/$(date +%Y)/$(date +%m)/teams.csv"
docker exec bashiri_db psql -U bashiri_user -d bashiri -c "\COPY (SELECT * FROM predictions_match) TO STDOUT WITH CSV HEADER" > "$CRITICAL_DIR/csv/$(date +%Y)/$(date +%m)/matches.csv"

# Generate checksums
sha256sum "$CRITICAL_DIR/pg_dump/bashiri_critical_$DATE.dump" > "$BACKUP_DIR/metadata/checksums/sha256sums_$DATE.txt"

# Upload to cloud storage (example: AWS S3)
# aws s3 sync "$BACKUP_DIR" s3://bashiri-backups/

# Cleanup old full backups (keep 7 days)
find "$FULL_DIR" -name "bashiri_full_*.dump" -mtime +7 -delete

echo "Backup completed: $DATE"
```

# Appendix C: Backup Command Reference

## C.1 pg_dump Commands

```bash
# Full database dump
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri -F c -f backup.dump

# Specific tables only
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri -t predictions_league -t predictions_team -F c -f backup.dump

# Schema only (no data)
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri --schema-only -f schema.sql

# Data only (no schema)
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri --data-only -f data.sql

# Plain SQL format
docker exec bashiri_db pg_dump -U bashiri_user -d bashiri -f backup.sql
```

## C.2 pg_restore Commands

```bash
# Restore from custom format
docker exec bashiri_db pg_restore -U bashiri_user -d bashiri -v backup.dump

# Restore to new database
docker exec bashiri_db pg_restore -U bashiri_user -C -d postgres backup.dump

# Restore specific tables
docker exec bashiri_db pg_restore -U bashiri_user -d bashiri -t predictions_league -t predictions_team backup.dump

# Clean before restore (drop existing tables)
docker exec bashiri_db pg_restore -U bashiri_user -d bashiri --clean --if-exists backup.dump
```

## C.3 CSV Export Commands

```bash
# Export entire table

```
